我看完了 project.md 和数据结构，建议你把这个题做成一个“面试友好”的版本：不追求大而全，重点突出你对金融文档问答系统的设计能力、工程完整性和取舍意识。

设计结论

最合适的是做一个 RAG + 结构化元数据过滤 + 可追溯引用 的财报问答系统，核心目标不是“模型多强”，而是：

能基于 2020–2025 年 AAPL 10-K 做准确检索。
回答里明确给出 年份 + section_title 引用。
对跨年份问题能做简单对比分析。
整个项目能本地一键跑起来，代码干净，README 讲清楚设计。
你这份数据本身已经按 section 切好了，这很重要，说明不要把系统设计得太重。没必要一开始就搞复杂 parsing pipeline，直接围绕“年报 section 级文档”做增强即可。

推荐架构

建议分 5 层：

ingest
读取 aapl_10k.json，把原始数据转成统一文档结构。
文档主键建议是：{year}_{section_id}

index
建两个索引：

稀疏索引：BM25，负责关键词精确召回
稠密索引：embedding，负责语义召回
retrieve
先做 query understanding，再做混合检索：

提取年份约束，如“2024”“近三年”
提取主题，如风险、营收、回购、诉讼、供应链
元数据过滤后，跑 BM25 + vector，再 rerank
generate
把 top-k 片段喂给本地模型生成答案，要求输出：

简洁结论
证据引用
如果证据不足，明确说不足
serve
提供一个简单 API 或 Web UI。
面试里建议优先做 API，再加一个很薄的页面。

数据建模

你的数据实际结构是“顶层 key 是 SQL 字符串，value 是 section 数组”，每条记录大致有：

symbol
file_fiscal_year
form_type
section_title
section_id
section_text
建议标准化成：

{
  "doc_id": "2025_7",
  "symbol": "AAPL",
  "year": 2025,
  "form_type": "10-K",
  "section_id": 7,
  "section_title": "Item 7. Management’s Discussion and Analysis...",
  "text": "...",
  "item_type": "MD&A"
}
这里的 item_type 很关键，建议你自己映射一层，把 section_title 归一成有限类别：

business
risk_factors
md&a
financial_statements
legal
executive_compensation
other
这样后面检索和 answer routing 都更稳。

切块策略

不要直接按固定长度粗暴切，建议：

先以 section 为一级文档。
对超长 section 再做二级 chunk，长度控制在 500-1000 tokens 左右。
chunk 之间保留少量 overlap。
表格类内容单独处理，不要和叙述段混在一起。
chunk metadata 建议包含：

year
section_title
item_type
chunk_id
chunk_order
这样回答时能回溯到具体 section。

检索策略

这个项目最值得讲的是“为什么不用单一向量检索”。

建议混合检索：

BM25 适合抓财务术语、专有名词、年份、会计项目
embedding 适合理解“某年风险变化”“供应链挑战”这类语义问题
推荐流程：

query 解析

是否有年份条件
是否是单年问答 or 跨年对比
是否是总结类问题
候选召回

BM25 top 10
vector top 10
合并去重

Reciprocal Rank Fusion 就够了
rerank

用轻量 reranker 或简单规则打分
年份命中、section 类型命中可加权
一个简单但很加分的规则：

问“风险”时，优先 Item 1A
问“经营表现/增长原因”时，优先 Item 7
问“财务数字/资产负债/现金流”时，优先 Item 8
这比纯模型“瞎找”更像工程化系统。

回答生成

生成层不要追求花哨，重点是可信和可解释。

建议 prompt 约束模型输出：

先回答结论
再列出证据
每条证据带引用
如果问题需要跨年比较，按年份分段
不允许编造数据；找不到就说不知道
输出格式建议：

结论：
...

依据：
- 2025, Item 1A Risk Factors: ...
- 2024, Item 7 MD&A: ...

补充说明：
...
这样面试官一眼能看出系统可追溯。

建议支持的 3 类问题

为了范围可控，系统只要做好这 3 类，已经很完整：

单点事实问答
例：Apple 2025 年主要风险有哪些？

跨年变化分析
例：2023 到 2025 年 Apple 在风险披露上有哪些变化？

简短报告生成
例：总结 Apple 近三年经营表现和主要风险，输出一段投资者视角摘要

这三类覆盖了检索、比较、总结，展示面足够大。

模型选择建议

题目要求本地开源模型，建议分两层：

embedding model：本地轻量 embedding
generation model：本地 instruction model，7B 级别就够展示
reranker：可选，没有也能做
这里不要把重点放在模型效果对比上，而是强调：

模型可替换
检索层是核心
生成只负责“基于证据组织答案”
这会显得你设计更成熟。

embedding模型可以使用本地的么，小参数的



上 1 条消息
可以，embedding 模型完全可以本地跑，而且这个项目我反而建议你优先用小模型本地化，不要把复杂度放到外部服务上。

结合你这个场景: AAPL 10-K 是英文语料，但你现在是中文在交流，所以我建议分两种路线。

更稳的选择

如果你希望“中文问题也能直接检索英文财报”，优先用 intfloat/multilingual-e5-small。它支持 94 种语言，模型卡写明是 12 层、384 维，比较适合本地小体量部署。这个方案的好处是你不用先把中文 query 翻译成英文。

如果你打算在检索前先把用户问题改写成英文，再去搜英文财报，那更推荐 BAAI/bge-small-en-v1.5。它是专门做英文检索的小模型，官方也把它定位成 small-scale 但检索能力有竞争力。对 10-K 这种英文金融文本，通常会比通用 multilingual 小模型更稳一些。

更轻的备选

如果你要极致轻量、CPU 先跑通，可以用 sentence-transformers/all-MiniLM-L6-v2。它只有 22.7M 参数，384 维，本地很好跑，适合先做 MVP，但它更像通用英文语义检索基线，不一定是你这个财报 RAG 的最终选择。

如果你想要质量再好一点、还想控制维度，nomic-embed-text-v1.5 也可以本地用，而且支持可调维度；但它相对更重，而且需要按模型卡要求加 search_document: / search_query: 前缀，工程上比前两个多一点约束。

我的建议

你这个项目最实用的选型是：

如果要直接支持中文提问: multilingual-e5-small
如果你愿意做“中文 query -> 英文检索 query”改写: bge-small-en-v1.5
如果只是先快速把系统跑起来: all-MiniLM-L6-v2
我个人会选第二种，也就是：

Chroma 做向量存储
bge-small-en-v1.5 做 embedding
中文问题先改写成英文检索 query
再配一个本地 BM25 做 hybrid retrieval
这样对英文 10-K 的命中率通常会更好。
